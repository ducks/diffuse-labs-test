# Dataset containment validation

This is a standalone code-repair task adapted from Replaybook Infra scenario
037 v4. It has its own verifier and results. See `PROVENANCE.md` for the pinned
source and differences; upstream model results are not reused as port scores.

## Reproduction

```sh
nix-shell --pure --run 'python scripts/validate_containment.py'
nix-shell --run 'python scripts/validate_containment.py --container'
nix-shell --run 'python scripts/validate_harbor.py --task dataset-containment'
```

## Controls

| Control | Local outcome | Docker reward |
| --- | --- | --- |
| Canonical persistent repair and receipt reconciliation | Pass | 1 |
| Alternative code-enforced loader policy, no root-config change | Pass | 1 |
| Restart only | Fail | 0 |
| Revoke access but leave refresh valid | Fail | 0 |
| Rotate credentials but leave the read boundary open | Fail | 0 |
| Leave unauthorized scheduling active | Fail | 0 |
| Disable all schedules, including legitimate reporting | Fail | 0 |
| Revoke the unrelated client's credential | Fail | 0 |
| Ignore interrupted jobs | Fail | 0 |
| Requeue and blindly republish existing outputs | Fail | 0 |
| Delete audit evidence | Fail | 0 |

Real Harbor oracle: **1 completed trial, 0 infrastructure errors, reward 1.0**.
Real Harbor nop: **1 completed trial, 0 infrastructure errors, reward 0.0**.
The script checks actual result JSON, not just the CLI exit status.

Two end-to-end test methods run fresh independent deployments. These contain
multiple HTTP, database, preservation, recovery, and lifecycle assertions;
they should not be described as the original branch's 23 unit tests.

The first reproduces the incident, starts client traffic, runs the submitted
repair in a separate process, and checks the result immediately and after two
restart cycles. The actual worker subprocess is terminated and recreated;
protected core HTTP servers are shut down and recreated inside the verifier.
The repair procedure is not rerun on these restarts. New ordinary and already
published/unacknowledged jobs are introduced in each phase.

The second reproduces the incident independently, verifies the repair, then
intercepts one queue acknowledgement with an explicit handler event after
publication. Recovery must adopt the existing receipt. It also re-presents a
previously acknowledged job as retry and checks that no output is republished.
An external publication witness records real output-service responses; final
receipts must match either trusted provisioning or those actual publications.

The verifier checks original datasets, accepted job identities and payloads,
result hashes, exactly one receipt/publication, the matching acknowledgement,
retained audit/export/receipt evidence, revoked original access and refresh,
derived access, unrelated client reads, cross-tenant denial, legitimate preview
contents, traversal and symlink denial, and continued legitimate reporting.

Live traffic is generated by a controller-owned thread outside the submitted
repair/worker processes and outside the deployment directory. Sampled client
reads and submissions must succeed; accepted jobs have a 15-second completion
deadline. Only verifier-controlled restarts are excluded from this window.
Deadlines and polling bound asynchronous observations; acknowledgement fault
injection uses an explicit event, not a sleep guessing the publication moment.

## Limits and difficulty

The model authors code before grading provisions the live fixture. This port
does not monitor live traffic during that earlier authoring stage. It tests the
repair procedure under traffic and persisted worker behavior afterward.

This container task is not the original NixOS deployment: it does not claim
host-reboot verification, separate service-user isolation, or a VM security
boundary between the verifier and arbitrary hostile submitted code. There is
one worker, no malicious file replacement race, and no arbitrary host power-loss
contract. The fixture contains synthetic data only and uses loopback HTTP;
container controls run with external networking disabled.

Functional controls validate the task but do not establish model difficulty.
The `hard` metadata is provisional. A new model pilot must be reported against
this port's task snapshot, not combined with the original scenario's pilot.
Full control logs and Harbor result JSON remain gitignored under
`logs/dataset-containment/` and `logs/harbor/`. Nothing is uploaded.

## First model pilot

A Codex CLI 0.164.0 / `gpt-6.1-sol` pilot at low reasoning effort passed both
end-to-end tests in **83.91 seconds** of agent execution, reward **1.0**, with
no infrastructure errors. The collected patch is a genuine receipt-reconciling,
credential-rotating repair. This does not establish hard difficulty. The
tracked report and submitted source are in
`../pilots/dataset-containment-codex-001/`. Original Replaybook pilot results
remain separate.
